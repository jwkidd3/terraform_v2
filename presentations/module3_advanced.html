☁️ Section 1: Terraform Cloud and Remote Execution

Why remote state and remote runs, and how to connect a configuration

🌟 Why Terraform Cloud? — Three Pillars

⚙️ Operational

  • Faster infrastructure provisioning
  • Reduced configuration drift
  • Centralized state management
  • Consistent execution environment

🤝 Collaboration

  • Shared remote state per workspace
  • Run history visible to the team
  • VCS integration (GitHub, GitLab, Bitbucket)
  • Private module registry

🔒 Governance

  • Audit trail of runs
  • Encrypted state storage
  • Role-based access control
  • Policy enforcement capabilities

🏠 Local Terraform — Team Challenges

⚠️ Business Risks

  • State File Loss: Lost or corrupted state means Terraform no longer knows what it manages
  • Credential Exposure: Credentials in local files
  • Compliance Failures: No audit trails or governance
  • Team Bottlenecks: Single points of failure

❌ Operational Limitations

  • State Management: Manual sharing, corruption risk, version conflicts
  • Security Exposure: AWS keys on laptops, unencrypted state, rotation gaps
  • Team Coordination: No locking, simultaneous modifications
  • Environment Drift: Inconsistent Terraform/provider versions
  • Audit: No change tracking or approval workflows

☁️ Terraform Cloud — What It Adds

🏆 Business Benefits

  • Productivity: Shared runners, no local setup to keep in sync
  • Risk Reduction: Locked, versioned state and reviewed plans
  • Compliance: Run history and policy checks support audits
  • Scale: Organizations, projects, and teams for many workspaces

✅ Enterprise Capabilities

  • Remote State: Automatic locking, versioning, encryption at rest
  • Secure Variables: Sensitive, write-only workspace variables and variable sets
  • Team Workflows: RBAC, approval processes
  • Audit: Full run history
  • Policy Enforcement: Sentinel and OPA policy sets

🔌 Connecting a Configuration: the cloud {} Block

terraform {
  required_version = ">= 1.9"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }

  cloud {
    organization = "user1-terraform-training"

    workspaces {
      name = "user1-terraform-cloud-lab10"
    }
  }
}
  • cloud {} lives inside the terraform {} block
  • It replaces backend "remote" — do not declare a backend block as well
  • organization = the org you created in the UI
  • workspaces { name = ... } pins this directory to exactly one workspace
  • terraform init makes the connection (and offers to migrate any existing local state)
Lab 10: replace the two placeholders in main.tf with your organization and workspace names. Org names are globally unique: if <username>-terraform-training was taken and you added a short suffix, use your actual org name here.

🏷️ Selecting Workspaces: name vs tags

Lab 10 — exactly one workspace

terraform {
  cloud {
    organization = "user1-terraform-training"

    workspaces {
      name = "user1-terraform-cloud-lab10"
    }
  }
}

Lab 11 — every workspace tagged lab11

terraform {
  cloud {
    organization = "user1-terraform-training"

    workspaces {
      tags = ["lab11"]
    }
  }
}
  • name locks the directory to one workspace — terraform workspace select has nothing to switch to
  • tags makes every workspace with all listed tags selectable from this directory
  • Lab 11 creates the workspaces from the CLI: terraform workspace new <name> creates a workspace that already carries the configured tags (so does terraform init when no tagged workspace exists yet and it asks for a name)
  • Fallback for a workspace made in the UI: Overview → Tags (right sidebar) → Manage Tags → key lab11, value empty; untagged workspaces stay invisible (“workspace not found”)

🧩 One Configuration, Workspace-Specific Values

variable "environment" {
  type = string # per workspace: "development" or "staging"
}

variable "instance_count" {
  type = number # per workspace: 1 or 2
}

resource "aws_instance" "app" {
  count         = var.instance_count
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

  tags = {
    Name        = "${var.username}-${var.environment}-instance-${count.index + 1}"
    Environment = var.environment
    Owner       = var.username
  }
}
Best Practice: drive differences with explicit workspace variables rather than branching on terraform.workspace — the values are visible and auditable in each workspace's Variables tab.

🗂️ Workspace Organization Strategies

By Environment

  • development - Low cost, fast iteration
  • staging - Production-like testing
  • production - Full scale, monitored

By Component

  • network - VPC, subnets, routing
  • security - IAM, security groups
  • application - EC2, S3, services
Best Practice: name workspaces <component>-<environment> and use tags (e.g. lab11, environment:staging) to group and filter them.
State isolation: each workspace has its own state file and run history — an apply in lab11-staging cannot touch lab11-development.

🔌 Connecting GitHub to Terraform Cloud

⭐ GitHub App (recommended)

  • Create a workspace → Version control workflow → GitHub.com
  • Install the Terraform Cloud GitHub App on your GitHub account when prompted
  • Grant it access to your lab repo (or all repos)
  • No OAuth app or client secret to manage

🔑 OAuth: “GitHub.com (Custom)”

  • Organization Settings → Providers → Add a VCS provider
  • Copy the Callback URL Terraform Cloud shows
  • GitHub → Developer settings → OAuth Apps → register an app with that callback
  • Paste Client ID + Client Secret back, then authorize
  • One-time setup per organization
Two different credentials: your GitHub Personal Access Token is only for git clone / git push from Cloud9. Terraform Cloud reads the repo through the GitHub App or OAuth connection.

🪝 Webhooks: Push → Run

git push origin main
→
GitHub webhook
→
Plan
→
Confirm & Apply
  • A VCS-driven workspace tracks one branch — the repo's default branch (main) unless you choose another
  • First run is manual: a brand-new workspace with no runs ignores webhooks — start it with New run → Plan and apply
  • After that, a push to the tracked branch queues a full run: plan, then apply after you click Confirm & Apply (or automatically with auto-apply)
  • Check the connection: workspace Settings → Version Control; GitHub repo Settings → Webhooks (OAuth) or the app's installation (GitHub App)
  • Variables still live in the workspace: credentials, username, aws_region are not committed; environment and app_version come from the committed terraform.tfvars
Lab 12 payoff: change app_version to v1.1.0, push, and watch the run replace the instance — no terraform command typed.

🔍 Speculative Plans on Pull Requests

git checkout -b feature/add-tags
# edit main.tf: add  CostCenter = "Training"  to common_tags
git add main.tf
git commit -m "Add CostCenter tag"
git push origin feature/add-tags     # push to a non-tracked branch: no run

# On GitHub: open a pull request  feature/add-tags → main
#   → Terraform Cloud runs a SPECULATIVE plan (plan only)
#   → the result appears as a status check on the pull request
# Merge the pull request → push to main → normal plan + apply
  • Speculative plan: shows what would change; it can never be applied and does not lock state
  • Triggered by pull requests against the tracked branch — not by plain pushes to other branches

  pull_request:
    branches: [main]

      - run: terraform init -backend=false
      - run: terraform validate
      - run: terraform test            # native tests in tests/*.tftest.hcl
      - name: Security scan (Trivy - tfsec is now part of Trivy)
        uses: aquasecurity/trivy-action@0.28.0
        with:
          scan-type: config
          scan-ref: .

  policy:
    runs-on: ubuntu-latest

Policy as code (next slides) checks every plan against organizational rules before apply — Terraform Cloud supports both Sentinel and OPA policy sets.

🛡️ Sentinel Policy as Code

restrict-ec2-and-rds.sentinel
import "tfplan/v2" as tfplan

required_tags = ["Environment", "Owner", "CostCenter"]
allowed_types = ["t3.micro", "t3.small", "t3.medium"]

# Managed resources being created or updated
changes = filter tfplan.resource_changes as _, rc {
	rc.mode is "managed" and
		(rc.change.actions contains "create" or rc.change.actions contains "update")
}
instances = filter changes as _, rc { rc.type is "aws_instance" }
databases = filter changes as _, rc { rc.type is "aws_db_instance" }

mandatory_tags = rule {
	all instances as _, rc {
		all required_tags as t { rc.change.after.tags contains t }
	}
}
approved_instance_types = rule {
	all instances as _, rc { rc.change.after.instance_type in allowed_types }
}
databases_encrypted = rule {
	all databases as _, rc { rc.change.after.storage_encrypted is true }
}

main = rule { mandatory_tags and approved_instance_types and databases_encrypted }

⚡ Open Policy Agent (OPA) / Rego (1/2)

policies/security.rego — OPA 1.0 syntax
package terraform.security

import rego.v1

required_tags := {"Environment", "Owner", "CostCenter"}

managed contains rc if {
	some rc in input.resource_changes
	rc.mode == "managed"
	some action in rc.change.actions
	action in {"create", "update"}
}

⚡ Open Policy Agent (OPA) / Rego (2/2)

policies/security.rego (continued) — deny rules
deny contains msg if {
	some rc in managed
	rc.type == "aws_security_group"
	some ingress in rc.change.after.ingress
	"0.0.0.0/0" in ingress.cidr_blocks
	ingress.from_port <= 22
	ingress.to_port >= 22
	msg := sprintf("%s allows SSH from 0.0.0.0/0", [rc.address])
}

deny contains msg if {
	some rc in managed
	rc.type in {"aws_instance", "aws_db_instance"}
	missing := required_tags - {key | some key, _ in rc.change.after.tags}
	count(missing) > 0
	msg := sprintf("%s is missing tags: %v", [rc.address, missing])
}

💰 Cost Control Policies

# policies/cost.rego - illustrative monthly costs
package terraform.cost

import rego.v1

monthly_cost := {"t3.micro": 8, "t3.small": 15, "t3.medium": 30, "t3.large": 60}
budget_limit := 200

instances contains r if {
	some r in input.planned_values.root_module.resources
	r.type == "aws_instance"
}

warn contains msg if {
	some r in instances
	cost := monthly_cost[r.values.instance_type]
	cost > 50
	msg := sprintf("%s uses %s (~$%d/month)", [r.address, r.values.instance_type, cost])
}

deny contains msg if {
	total := sum([monthly_cost[r.values.instance_type] | some r in instances])
	total > budget_limit
	msg := sprintf("Estimated $%d/month exceeds budget of $%d", [total, budget_limit])
}

🏷️ Resource Tagging Strategy

locals {
  # Standard tags applied to all resources
  standard_tags = {
    Environment = var.environment
    Project     = var.project_name
    Owner       = var.username
    ManagedBy   = "Terraform"
    Repository  = var.git_repository
    CostCenter  = var.cost_center
    DataClass   = var.data_classification
    Backup      = var.backup_required ? "daily" : "none"
  }
}

# Apply tags automatically using provider default tags
provider "aws" {
  region = var.aws_region

  default_tags {
    tags = local.standard_tags
  }
}
Avoid timestamp() in tags: it returns a new value on every run, so every plan shows changes. Use static values (or a CI-supplied variable) instead.

⚡ Section 6: Performance Optimization and Scaling

Keeping large configurations fast and maintainable

📈 Large-Scale Terraform Optimization

State Management

  • Split state by component (one workspace each)
  • Keep each workspace small and focused
  • Rely on built-in state locking
  • Remove unused resources from configuration

Resource Planning

  • Use -target only for exceptional cases
  • Tune -parallelism for large graphs
  • Minimize provider calls
  • Share outputs between workspaces instead of re-querying
# Performance tuning (local or CLI-driven runs)
export TF_CLI_ARGS_plan="-parallelism=20"
export TF_CLI_ARGS_apply="-parallelism=20"

# Target specific resources (exceptional use only)
terraform apply -target=module.network.aws_vpc.main
